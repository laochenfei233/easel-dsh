# 热点雷达 v2：从「看榜单」到「看信号」，右键留住正文

## Report

（设计阶段，待实现后回填）

## [S1] Problem

现状（`TrendsPage.tsx` + 宿主半 `index.js` 的 `/api/trends`）已经能拉 6 个内置平台热榜、
自定义 RSS/JSON 源、分类筛选、应用内代理，以及「收藏到选题库 / 做成内容」。但对创作者
真正要做的判断——「这条值不值得现在蹭」——页面给不出信息：

1. **只有此刻的名次，没有时间维度。** 每次刷新只看到当前 top 15，无法区分「刚冲上来的
   第 8」和「已经挂了 12 小时的第 3」。蹭热点拼的是时间窗，名次本身不说明升温还是退潮。
2. **同一事件散落在多列。** 微博、抖音、知乎、头条对同一件事用不同标题，用户得自己在
   6 列 × 15 条里肉眼串起来。真正强的信号是「多平台同时在榜」，页面上反而看不到。
3. **没有个人视角。** 90 条标题里和账号赛道相关的通常只有个位数，每次都要重扫。自定义源
   的「分类」只解决源的分组，解决不了「词」的关注。
4. **快照只活在进程内。** `TREND_CACHE` 是内存 Map：应用重启或上游连续失败后页面直接
   空白，即使几分钟前刚拿到过数据；内置源是第三方镜像，偶尔全挂。
5. **看到新闻后，正文还得自己再抓一遍。** 现有「收藏」只存标题与来源；想留正文得点开
   原文、复制、再回选题库补备注，agent 做内容时也要重新联网。热点页到选题库之间断了
   一段最该自动化的路。

参考了 `brook-reader` 的 RSS 阅读器 spec 的「多源、板块、本地持久化」问题意识，但本草稿
不引入阅读器语义：不做已读/未读、不做 OPML、不做全文缓存、不在刷新链路里调用 LLM。

## [S2] Design

### 原则

- 不新增依赖：聚类、轨迹、关注词全部用现有 Node/浏览器能力。
- 刷新链路不调 LLM：热点页的响应时间取决于上游，不应再叠加模型延迟与费用；AI 仍只在
  用户点「做内容」后进入（现有 `topicPrompt` 已要求先判断适不适合账号赛道）。
- 只加一个落盘文件（`_radar_history.json`），它是缓存，可随时删除；不改变
  `_radar_config.json` 的既有字段语义。
- 现有调用方（工作台的 `fetchTrends('weibo,douyin', 6)`）不感知新逻辑：新增字段全部可选，
  默认 `view=list`；分列排序是前端行为，不新增服务端参数。

### D1 轨迹存储（`outputs/_radar_history.json`）

```json
{
  "version": 1,
  "sources": {
    "weibo": {
      "at": 1760000000,
      "items": [
        {
          "key": "苹果2026发布会官宣",
          "title": "苹果 2026 发布会官宣",
          "url": "https://s.weibo.com/...",
          "hot": "123万",
          "firstSeen": 1759990000,
          "lastSeen": 1760000000,
          "lastRank": 4
        }
      ]
    }
  }
}
```

- **源键**：内置用平台键（`weibo`…）；自定义源沿用现有的 `custom:<name>`。改名等于新源，
  轨迹从零开始（已知且可接受）；同名换 URL 视为同源（同一订阅的镜像切换）。
- **条目键**：`normalizeTrendTitle(title)`——NFKC、转小写、去掉空白与标点，截断 120 字符。
  标题是热榜里最稳定的字段；URL 常带跳转参数，不做主键。
- **合并**：每次成功抓取后，用上一份快照的键集合判断 `isNew`；`delta = 上一份 lastRank -
  本次 rank`，新条目没有 `delta`。`firstSeen` 只在首次出现时写，`lastRank` 每轮覆盖。
- **上一份快照必须够新**：该源的 `at` 距本次超过 30 分钟时（应用关了很久、隔夜再开），
  不计算 `isNew`/`delta`，把这次当作新基线。否则重启后会把整张榜误标成「新」。下一次
  刷新（带 `force`，或距本次超过 300s 的普通刷新）就会开始出徽标。
- **抓全再截断**：合并用抓取到的完整列表（真实榜位 `rank` 1..n），`limit` 只作用于响应。
  这样第 16 名之后的升跌也能被下一轮感知。
- **解析出 0 条算抓取失败**：不写历史、不推进 `at`、不更新内存缓存，走 D2 的失败链。上游
  改版返回 200 + 空数组时，不能把整张榜误判成「全部下榜」。
- **保留**：每源最多 200 条，`lastSeen` 超过 72 小时的条目不参与下一轮合并（热榜话题的
  生命周期远短于 72 小时）。写盘在请求内最多一次；单进程内并发请求采用 last-write-wins
  （丢的只是缓存元数据，下一轮自愈，不做互斥）。
- **写失败不失败请求**：落盘失败只丢轨迹，不影响本次页面数据；读写异常一律按空历史处理。
- **版本/损坏**：`version !== 1` 或结构不合法一律当空文件处理。

### D2 `/api/trends`：派生字段、离线兜底与排序

新增查询参数：

| 参数 | 取值 | 默认 | 语义 |
|---|---|---|---|
| `view` | `list` / `cluster` | `list` | `cluster` 时响应额外带 `clusters` |
| `force` | `1` | 无 | 跳过 300s 内存缓存重新抓取（页面「刷新」按钮用；挂载加载不用） |

每个 `items[]` 新增：

```ts
{
  rank: number,        // 真实榜位（1 起），不随排序变化
  delta?: number,      // 正=上升，负=下降；新上榜或上一份快照超过 30 分钟时缺省
  isNew?: boolean,     // 上一份新近快照里没有
  ageMin?: number,     // 首次出现至今分钟数（响应时计算，钳到 ≥ 0）
  watch?: string[]     // 命中的关注词
}
```

每个 `TrendGroup` 新增：`at?: number`（该源数据时间）、`stale?: boolean`（内容不是本轮抓的）、
`category?: string`（自定义源沿用，类型补齐）。

响应新增：

```ts
watch: { keyword: string; items: ClusterItem[] }[]   // 按关注词分组
clusters?: TrendCluster[]                             // 仅 view=cluster
updated: number                                        // 各源 at 的最大值（不再是请求时刻）
```

- **失败链（逐源）**：内存缓存（≤300s 且非 force）→ 抓取 → 失败时用内存里最近一次成功
  快照（数据 ≤ 24h，标 `stale: true`）→ 没有内存快照再读落盘（`lastSeen` ≤ 24h，标
  `stale: true`）→ 空列表 + `ok: false`。超过 24h 的一律不显示，避免把三天前的热搜当实时榜。
- **`ok`**：有内容即 true（含 stale）；完全无内容 false。客户端空态按 `stale` 与 `ok` 区分
  「离线快照」「暂时取不到」。
- **兼容**：老客户端忽略新增字段；`updated` 从「请求时刻」改为「数据时刻」，页头时间更准确
  （工作台不展示该字段）。
- **关注匹配**只作用于本次返回的源集合（选中的内置平台 + 启用的自定义源），与页面所见一致；
  取消勾选某平台，它的命中同时消失。

### D3 跨平台聚合（`view=cluster`）

把「同一事件」合成一张卡：

```ts
{
  id: string, title: string,           // 代表标题 = 簇内名次最好那条
  platforms: string[], labels: string[],
  bestRank: number, firstSeen: number, isNew: boolean,
  items: { platform, label, title, url, hot, rank, delta?, isNew?, watch? }[]
}
```

- **相似判定**（无模型、可解释）：
  - 标题先 `normalizeTrendTitle`；不足 4 字的标题只接受完全相同（避免「官宣」「分手」这类
    短词误并）。
  - 取字符 bigram 集合；`相似度 = |交集| / min(|A|, |B|)`（短标题被长标题包含时仍能命中）。
    `相似度 ≥ 0.6` 且共享 bigram ≥ 2 判同题。
  - 归一化 URL 相同（且非空）直接并入。
- **贪心成簇**：按源顺序、榜位从高到低扫描，与已有簇的**代表标题**比较，命中即并入，否则
  新开一簇。只比代表项会漏掉部分传递相似（`ponytail:` 足够；误并/漏并明显时再换全成员比较
  或 embedding）。
- **排序**：平台数降序 → 最好名次升序 → 首次出现时间升序。`platforms`/`labels` 按平台去重
  （同一源的相近条目仍留在同一簇的 `items` 里）；单平台条目保留在结果里（排在多平台簇
  之后），聚合视图可独立替代分列视图。最多返回 60 簇。
- **动作**：卡片上的「收藏 / 做内容」用代表标题；收藏 source 记
  `跨平台热搜（微博/抖音）`。
- **筛选**：分类 chip 只作用于分列视图；聚合视图隐藏分类行（聚合的对象是跨类别的事件）。
- **载荷**：`clusters[].items` 复用 `trends` 里的条目信息，字段有重复；当前规模（≤8 源 × 30 条）
  下多几十 KB，不值得为省这点做引用协议。

### D4 关注词

- 配置：`_radar_config.json` 新增 `keywords: string[]`（≤20 个，每个 1–24 字符，trim、去空、
  大小写不敏感去重）。旧文件缺字段 = 空。
- 匹配：`normalizeTrendTitle(title)` 包含 `normalizeTrendTitle(keyword)` 即命中（中文子串 +
  英文忽略大小写足够；不做分词/同义词）。
- 响应：`watch` 按关键词分组，组内按 `isNew` → 真实名次排序，每组最多 10 条。
- 页面顶部「我的关注」卡：仅在有命中时出现；每个关键词一行 chip + 命中条目（复用趋势行
  组件，带平台标签）；副标题显示 `命中 N 条 · 新 X`。最多展示 5 个命中词、每词 3 条，超出
  收成「还有 N 条」，避免关注词把首屏撑爆。
- 设置抽屉加「关注词」输入：逗号/空格分隔，保存时规范化；helper 说明「用于在热点页置顶你
  关心的词」。

### D5 页面

- 控制区：内置平台 chips（不变）+ 分类 chips（仅分列）+ 视图切换 `分平台 | 聚合` + 排序切换
  `榜序 | 升温`；「刷新」按钮带 `force=1`。
- 排序：`升温` 纯前端重排（`isNew` 真优先 → `delta` 缺省 0 降序 → 真实名次升序），不重新
  请求；名次列始终读 `it.rank`，不读数组下标。
- 视图：首次切到聚合时带 `view=cluster` 重新请求（响应里仍含 `trends`，切回分列不重取）。
- 分列：列头显示源名与条目数；`stale` 列显示「离线 · 上次 HH:MM」；条目行 = 真实名次 +
  标题 + 热度 + 徽标（`新` / `↑3` / `↓2` / 关注词）+ 收藏/做内容；`ageMin ≥ 60` 时在热度后
  补一行 `首现 Xh`（不占新列，长标题仍单行省略）。`ageMin` 是「首次出现至今」，不是连续在榜
  时长；中间掉榜再回榜会显示更早的首现时间。
- 聚合：卡片网格，卡头代表标题 + 平台标签 + 「N 平台在榜 · 最高第 X」；卡体逐平台列原始
  标题、名次、徽标。平台标签最多展示 4 个，其余收成 `+N`。
- 行组件统一：现有 `customGroups` 与 `builtinGroups` 的两段重复 JSX 合成一个 `TrendColumn`
  （空态文案按 `ok/stale` 分支），徽标与动作逻辑只写一次。
- 样式同时补 `src/styles/index.css` 与 `src/styles/apple.css`（两套主题都过一遍），沿用现有
  `.trend-*` 命名。

### D6 右键抓取正文（内容库 + 选题库）

**交互**

- 趋势行（分列、聚合卡、我的关注复用同一个 `TrendRow`）带 `data-easel-trend` 属性，值是
  `{title,url,source,platform,rank,hot}` 的 JSON。`source` 是最终写入选题的来源文案
  （`微博热搜` / `跨平台热搜（…）`），书签与右键共用同一份计算。全局右键菜单
  （`context-menu.js`）的 `resolveSurface` 新增 `trend` 面：`target.closest
  ('[data-easel-trend]')` 且 payload 有 `title` 时接管；判定顺序在 file 之后、editable
  之前（趋势行不在模态/输入框里，不冲突）。
- 菜单：`抓取正文并入库`（主操作；无 `url` 时禁用并提示「无原文链接」）、
  `仅收藏标题到选题库`、分隔线、`复制标题`、`复制原文链接`（无链接禁用）、
  `打开原文`（无链接禁用）。
- 动作走 HTTP，不依赖 React 状态；完成后用菜单自带的轻量 toast 报结果，并派发
  `easel:trend-saved` 让趋势页把书签置为已存（与左侧按钮状态同步）。
- 左侧书签按钮保持轻量（只存标题），正文抓取只在右键菜单显式触发——避免误点发网络请求。

**接口 `POST /easel/api/radar/article`**

请求 `{title, url, source, platform, rank, hot}`；响应
`{ok, idea, bodyPath, chars, reused, warning?}`。

1. **URL 安全**：仅 `http`/`https`；拒绝带用户名/密码的 URL；拒绝 loopback、私网、
   链路本地与 `.local` 主机（包括解析后的 A/AAAA 记录），跟随最多 3 次跳转且每跳重新
   校验。热榜链接来自第三方，不能当本地可信输入。
2. **抓取**：复用 `rawRequest` 的代理能力（`proxyEnabled` 时走配置代理），桌面 UA +
   `accept-language: zh-CN`，15s 超时，5MB 上限；`rawRequest` 增加返回响应头（现有调用方
   忽略），用于 `content-type` / `location` / charset；按 `content-type` / `<meta charset>`
   解码（UTF-8 优先，GBK 等用 `TextDecoder`，不支持时回退 UTF-8）。
3. **提取** `extractArticle(html)`：去掉 script/style/noscript/svg/iframe/form/nav/
   header/footer/aside；优先 `<article>` → `<main>` → `<body>`；取 `<p>` 文本按空行
   拼接，没有足够 `<p>` 时退化为整段去标签文本；解实体、压空白、最多 100k 字符。
   标题取 `og:title` → `<title>` → 行标题；描述取 `og:description` / meta description
   作摘要兜底。
4. **降级**：登录/验证码页、`content-type` 非 HTML、HTTP 非 2xx、超时——不写正文文件。
   提取到 0 字符同样不写；提取到 < 200 字符但不像登录页时照写并标 `正文过短`（可能是
   不完整的短讯）。无论正文是否可得，**仍创建/复用选题**（标题、来源、原文链接），不写
   空文件、不拿登录页冒充正文；响应带 `warning`（`需登录` / `上游返回 403` / `正文过短`
   / `抓取超时`）。
5. **写内容库**：`outputs/热点正文/<slug>-<urlHash8>.md`（目录自动建，临时文件 + rename
   原子写）。文件头用引用块，不用 YAML frontmatter——内容库的 markdown 预览会把 `---`
   渲染成分隔线：

   ```markdown
   # <标题>

   > 来源：微博热搜 · 第 3 名 · 热度 123万
   > 原文：https://…
   > 抓取：2026-10-23 12:34

   <正文段落…>
   ```

   图片/视频不下载，原文链接保留。
6. **写选题库**：`_ideas.json` 按 `url` 精确匹配。
   - 命中：复用该选题，更新 `url`/`bodyPath`；抓取成功时重写内容文件；**不覆盖用户改过
     的 title/note/status**（`note` 为空时才填摘要），`reused: true`。
   - 未命中：`unshift` 新条目 `{id, title, note: 摘要, source: source || '热点雷达',
     status: 'pending', created, url, bodyPath}`。
   - `bodyPath` 是 outputs 相对路径（`热点正文/xxx.md`），只由服务端写；通用
     `POST/PUT /api/ideas` 不接受该字段，避免借路径读任意文件。
   - `_ideas.json` 的读改写收敛到 `mutateIdeas(settings, fn)` 串行队列，创建/更新/删除/
     本接口共用。新增第二个写者后，原先的并发覆盖风险会变成真的丢选题。
7. **失败语义**：URL 非法 → 400，不建选题；抓取失败但选题写成功 → 200 + `warning`
   （用户至少拿到标题与链接）；选题写盘失败 → 5xx，不谎报成功；内容文件写失败 → 选题
   照建，响应提示正文未保存（下次重抓可补）。
8. **可测性**：抓取与 DNS 校验做成可注入的函数参数（路由用真实实现），单测用本地 HTML
   fixture 覆盖提取、降级分支与选题 upsert，不联网。

**选题卡片**

- `Idea` 类型加 `url?` / `bodyPath?`。卡片有 `bodyPath` 时显示「正文」按钮，点开用
  `fetchOutputContent(bodyPath)` + `renderMarkdown` 的只读弹窗；正文只存内容库一份，
  不在 `_ideas.json` 复制全文，避免选题列表载荷膨胀。
- 有 `url` 时显示「原文」外链。删除选题不联动删除内容库文件；删除文件后「正文」按钮
  报文件不存在（文件归内容库管理，可接受）。
- 选题卡「做内容」把 `bodyPath` 作为 `useTopic` 的第三参数；`topicPrompt` 末尾追加一行
  `<projectRoot>/outputs/<bodyPath>` 的绝对路径，agent 先读正文再动笔。路径解析失败时
  忽略这行，不影响原有流程。

**已知边界**

- 微博搜索页、抖音视频页、登录墙、纯 JS 渲染页通常抓不到正文；降级为标题+链接并明确
  提示，不拿登录页冒充正文。
- 同一 URL 重复右键：选题不重复、文件重写；同一 URL 改标题不会新建文件（复用已有
  `bodyPath`）。URL 带不同跟踪参数会被当成不同文章，暂不做参数归一化。
- 聚合卡右键用代表标题与 `跨平台热搜（…）` 来源；卡内其他平台条目仍可单独右键。
- 正文是纯文本，不含图片、视频、评论；需要这些仍打开原文。

### D7 边界与已知上限

- 上游返回同一标题重复：按 `key` 合并，响应去重；标题相同但 URL 不同的条目保留一条。
- 自定义源改名 = 新源，轨迹/关注历史清零；换 URL 但同名视为同源。
- 时钟回拨：`firstSeen > now` 时按 now 处理，`ageMin` 钳到 0。
- 聚合误并：卡片逐条展示原始标题，合并依据可见；阈值是模块内常量，不做 UI 配置。
- `ponytail:` 聚类是 O(n·k) 的字符 bigram 比较（8 源 × 30 条 ≈ 数百次），不做索引；关注词是
  子串匹配，不做分词；轨迹写入无互斥，last-write-wins。
- 刷新粒度 = 300s 缓存周期；想立刻看升跌就连点两次「刷新」（第二次 force），但轨迹本身仍
  以真实抓取时刻为准。

## [S3] Scope

**In scope**

- `outputs/_radar_history.json` 轨迹存储、合并、裁剪、离线兜底
- `/api/trends` 派生字段、`view`/`force` 参数、`watch`/`clusters` 响应
- `_radar_config.json` 的 `keywords` 读写与校验
- 热点页：视图/排序切换、徽标、真实名次、离线提示、聚合卡片、我的关注、设置里的关注词
- 趋势行右键菜单：抓取原文正文 → 内容库 `热点正文/` + 选题库（带 `url`/`bodyPath`）
- 选题卡「正文」只读预览与「原文」外链
- 两套主题样式
- 纯函数单测（轨迹/聚类/关注词/正文提取/URL 安全）+ 配置、损坏文件、并发写选题回归；构建与页面冒烟

**Out of scope**

- 已读/未读、收藏夹式阅读器、OPML 导入、全文缓存、后台定时刷新（参考 spec 的阅读器语义）
- 刷新链路里的 AI 分类/摘要/评分（继续只在「做内容」后由 agent 处理）
- 新内置平台/新抓取器（自定义 RSS/JSON 已覆盖；坏一个源不加维护面）
- 通知/推送、跨设备同步
- 聚合的历史曲线图（有轨迹后可作为下一步）
- 正文中的图片/视频/评论抓取、OCR、付费墙绕过、登录态抓取（需要时打开原文）
- 热榜条目没有原文链接时用搜索引擎补全文章（只存标题+链接，不猜正文）
- URL 跟踪参数归一化（`utm_*` 等不同参数会当成不同文章）
